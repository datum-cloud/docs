This page shows how to require people to sign in with Google before requests reach your app, and how to limit access to your Workspace domain or to a list of people. It uses an [Envoy Gateway](https://gateway.envoyproxy.io/) `SecurityPolicy`. For how OIDC sign-in works with any provider, see [Sign in with OIDC](/alb/authentication/oidc).

<Warning>
  On its own, Google sign-in lets in **anyone with a Google account**. To limit who gets in, follow [Restrict who can sign in](#restrict-who-can-sign-in) too.
</Warning>

## Before you start

- A load balancer, ideally with a [custom hostname](/alb/operations/custom-domains). The redirect URL you register with Google has to match exactly, so use a hostname that won't change.
- A Google Cloud project where you can create OAuth credentials.

## Step 1: Create a Google OAuth client

1. In the [Google Cloud console](https://console.cloud.google.com), go to **APIs & Services** → **Credentials**.
2. Select **Create Credentials** → **OAuth client ID**. If asked, configure the consent screen first.
3. Set **Application type** to **Web application**.
4. Under **Authorized redirect URIs**, add `https://HOSTNAME/oauth2/callback`, with your load balancer's hostname.
5. Select **Create**, and copy the **Client ID** and **Client secret**.

If your organization uses Google Workspace, you can set the consent screen's **User type** to **Internal**. Google then signs in only accounts in your Workspace organization.

## Step 2: Store the client secret

Save this as `google-secret.yaml`, with your client secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ALB_NAME-oidc
  labels:
    networking.datumapis.com/gateway-sync: "true"
type: Opaque
stringData:
  client-secret: YOUR_CLIENT_SECRET
```

```bash
datumctl apply -f google-secret.yaml
```

The Secret must use the key `client-secret` and carry the `gateway-sync` label. Without the label, every request returns `500`.

## Step 3: Apply the SecurityPolicy

Save this as `google-oidc.yaml`, with your client ID and hostname:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: ALB_NAME-oidc
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: ALB_NAME
  oidc:
    provider:
      issuer: https://accounts.google.com
    clientID: 1234567890-abc123.apps.googleusercontent.com
    clientSecret:
      name: ALB_NAME-oidc
    redirectURL: https://app.example.com/oauth2/callback
    logoutPath: /logout
    scopes:
      - openid
      - email
      - profile
```

```bash
datumctl apply -f google-oidc.yaml
```

Allow up to a minute for the policy to reach every location.

## Step 4: Check it

```bash
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://app.example.com/
```

An anonymous request returns `302` to `https://accounts.google.com/o/oauth2/v2/auth?...`. In a browser, sign in with Google, and you land on your app.

## Restrict who can sign in

To decide who gets in at the load balancer, add a `jwt` block that checks the ID token Google returned, and an `authorization` rule on its claims. Replace the policy from Step 3 with this one:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: ALB_NAME-oidc
spec:
  targetRefs:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      name: ALB_NAME
  oidc:
    provider:
      issuer: https://accounts.google.com
    clientID: 1234567890-abc123.apps.googleusercontent.com
    clientSecret:
      name: ALB_NAME-oidc
    redirectURL: https://app.example.com/oauth2/callback
    logoutPath: /logout
    scopes: [openid, email, profile]
    cookieNames:
      idToken: id-token          # a fixed name, so the jwt block can find it
  jwt:
    providers:
      - name: google
        issuer: https://accounts.google.com
        audiences:
          - 1234567890-abc123.apps.googleusercontent.com   # your client ID
        remoteJWKS:
          uri: https://www.googleapis.com/oauth2/v3/certs
        extractFrom:
          cookies: [id-token]
        claimToHeaders:
          - claim: email
            header: X-User-Email
  authorization:
    defaultAction: Deny
    rules:
      - name: our-workspace
        action: Allow
        principal:
          jwt:
            provider: google
            claims:
              - name: hd
                values: ["example.com"]
```

People outside the rule can still sign in with Google, but they get `403` from the load balancer. Your origin receives each allowed person's address in `X-User-Email`.

Choose the claim to match:

| To allow | Claim | Values |
| --- | --- | --- |
| Everyone in a Google Workspace domain | `hd` | `["example.com"]`. Only Workspace accounts carry `hd`, so personal Gmail accounts are refused. |
| Specific people | `email` | `["alice@example.com", "bob@example.com"]` |
| Specific people, by an ID that never changes | `sub` | Google's numeric account IDs |

Values match exactly, with no wildcards, so `*@example.com` matches no one. To allow several domains, list them all in `values`. For more rules, see [Authorization rules](/alb/authentication/authorization).

Google's access token isn't a JWT, so the `jwt` block reads the **ID token** cookie, as above, not the `Authorization` header.

## Remove Google sign-in

Delete the policy and the Secret while the load balancer still exists:

```bash
datumctl delete securitypolicy ALB_NAME-oidc
datumctl delete secret ALB_NAME-oidc
```

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `500` on every request | The Secret is missing the `gateway-sync` label, or its name doesn't match `clientSecret.name`. | Add the label, and check the name. |
| `Error 400: redirect_uri_mismatch` from Google | The redirect URL isn't registered. | Add `redirectURL` exactly to **Authorized redirect URIs**. |
| A redirect loop after signing in | `redirectURL` uses a different hostname than the one in the browser. | Use one hostname, and set `redirectURL` to it. |
| `403` after signing in, for everyone | The ID token cookie name doesn't match `extractFrom`, or `audiences` isn't your client ID. | Set `cookieNames.idToken` and `extractFrom.cookies` to the same name. Check `audiences`. |
| `403` for a personal Gmail account | The `hd` rule is working. Gmail accounts have no `hd` claim. | Allow them by `email` instead, if they should get in. |
| `401` after signing in | The `openid` scope is missing, or the client secret is wrong. | Include `openid`, and re-create the Secret. |

## Good practice

- Register a separate OAuth client for each environment, such as staging and production.
- Register only the redirect URIs you use.
- Rotate the client secret from time to time, then apply the Secret again.
