An NLB accepts traffic on **listeners**, sends it to backends through **routes**, and gets its public IPv6 addresses and generated hostnames from **address requests**. This page covers each, and how to change them on a running NLB. To create your first NLB, see [Operations](/nlb/operations).

<Note>
  NLBs are in early access, and the `networking.datumapis.com/v1alpha` API can change. See [Limitations and roadmap](/nlb/limitations-and-roadmap).
</Note>

## A complete example

The following manifest publishes a Postgres workload on public TCP port `5432`. It has one NLB with one listener, and one route that sends the listener's traffic to the `postgres` port of a network service named `db`:

```yaml db-nlb.yaml
apiVersion: networking.datumapis.com/v1alpha
kind: NetworkLoadBalancer
metadata:
  name: db-nlb
spec:
  networkRef:
    name: default            # the gVPC network of your Instances
  exposure:
    addresses:
      - name: tcp-5432       # an address request: an IPv6 address and hostname in each location
        families: ["IPv6"]
  listeners:
    - name: tcp-5432
      protocol: TCP          # TCP or UDP
      port: 5432             # the public port that clients connect to
      addressRefs: ["tcp-5432"]
---
apiVersion: networking.datumapis.com/v1alpha
kind: NetworkLoadBalancerRoute
metadata:
  name: db-nlb-tcp-5432
spec:
  parentRefs:
    - name: db-nlb
      listener: tcp-5432     # the listener that this route serves
  backends:
    - networkService:
        name: db             # selects your workload's Instances
        port: postgres       # the name of a port on the network service, not its number
      healthCheck:
        protocol: TCP
```

The rest of this page covers each part. For a walkthrough that also creates the backend, see [Operations](/nlb/operations).

## Listeners

A listener is an entry in the NLB's `spec.listeners`. It accepts one protocol on one public port.

| Field | Description |
| --- | --- |
| `name` | Required. The name that routes use to attach to this listener. Unique within the NLB. |
| `protocol` | Required. `TCP` or `UDP`. |
| `port` | The public port, from `1` to `65535`. |
| `addressRefs` | Required. The address request whose addresses this listener serves on. In early access, list exactly one, and give every listener its own address request. See [Address requests](#address-requests). |

An NLB takes up to 16 listeners. The [Cloud Portal](https://cloud.datum.net) names each listener and its address request after its protocol and port, such as `tcp-5432` or `udp-7777`, and the manifests in these docs follow the same pattern.

The API also has `portRange`, `hostname`, and `tls` fields, and a `TLS` protocol. Early access refuses them. See [Limitations and roadmap](/nlb/limitations-and-roadmap).

### Address requests

An address request is an entry in `spec.exposure.addresses`. Datum gives it a public IPv6 address and a generated hostname in each location, and a listener refers to it by name in `addressRefs`.

| Field | Description |
| --- | --- |
| `name` | Required. A name for the address request, up to 63 lowercase letters, numbers, and hyphens. |
| `families` | Required. `["IPv6"]`. Early access refuses `IPv4`. |
| `locations` | Optional. Which locations get an address. See [Choose locations](#choose-locations). |

In early access, each listener needs its own address request, and two listeners can't share one. So an NLB with a TCP listener and a UDP listener has two IPv6 addresses and two hostnames in each location, one for each listener. An NLB takes up to 16 address requests.

### TLS traffic

A `TCP` listener forwards TLS traffic unchanged. Your workload keeps its own certificate and completes the TLS handshake with the client, and Datum never sees the decrypted traffic. Datum doesn't issue certificates for NLB hostnames, so get a certificate for a domain that you own and point that domain at the NLB. See [Use your own domain](#use-your-own-domain).

## Routes

A route is a separate `NetworkLoadBalancerRoute` resource. It attaches to a listener and names the backend, as in the [example](#a-complete-example).

| Field | Description |
| --- | --- |
| `parentRefs[].name` | Required. The NLB's name. The NLB must be in the same project. |
| `parentRefs[].listener` | The listener's name. Set either `listener` or `port`. |
| `parentRefs[].port` | The listener's port, instead of its name. |
| `backends[].networkService.name` | Required. The network service that selects your Instances. |
| `backends[].networkService.port` | Required. The **name** of a port on the network service, such as `postgres`, not its number. |
| `backends[].healthCheck` | How Datum checks each Instance. Required for a UDP listener. See [Health checks](/nlb/health-checks). |

Keep the following points in mind:

- **One backend for each route.** In early access, `backends` takes exactly one entry. To spread traffic across Instances, scale the workload behind the network service instead.
- **The protocols must match.** The network service port's protocol must match the listener's protocol: a `TCP` port for a `TCP` listener, and a `UDP` port for a `UDP` listener. A mismatch reports `ProtocolMismatch`.
- **The network must match.** The network service must select Instances on the NLB's network. Otherwise, the route reports `NetworkMismatch`.
- **Create in any order.** You can create the route before its NLB or network service exists. It reports what it's waiting for, and starts serving when everything it refers to exists. An NLB doesn't get an address until a route with running Instances attaches to its listener.
- **Deleting doesn't check routes.** You can delete an NLB or a network service that a route still uses. The route then reports `ParentNotFound` or `BackendNotFound`, and still counts toward your route quota. See [Delete an NLB](/nlb/operations#delete-an-nlb).

The Cloud Portal names the route `<nlb>-<listener>`, such as `db-nlb-tcp-5432`.

### Port mapping

The listener's `port` is the port clients connect to. The network service port is the port your app listens on. They don't have to be the same. For example, a listener on port `5432` can send traffic to a network service port named `postgres` with the number `15432`. Clients connect to `5432`, and your app sees connections arrive on `15432`.

### One route for each listener

A listener serves one route at a time. If two routes attach to the same listener, the older route keeps the listener, even if it's broken, and the newer route reports `Superseded` until the older one is deleted. Each route's `status.parents[].effective` field shows whether it owns the listener.

A network service port can be the backend of only one route. A second route, on this NLB or another one, that sends traffic to the same network service port reports `BackendClaimConflict`, and its listener doesn't serve. To put the same app behind two listeners or two NLBs, make it listen on a second port, and add that port to the network service under its own name. A port can still be the health check port of other routes.

## The network

An NLB serves one [gVPC network](/galactic-vpc/networks/overview), set in `spec.networkRef.name`, usually `default`. You can't change the network after you create the NLB. The network must carry IPv6. Instances' IPv6 addresses are how Datum reaches them.

## Choose locations

By default, an address request gets an address in each location where the backend's Instances run. If you add the workload to another supported location, the NLB gets an address there too, and the addresses in the other locations don't change.

To choose locations yourself, set `locations`:

```yaml
addresses:
  - name: tcp-5432
    families: ["IPv6"]
    locations:
      from: Names
      names: ["us-east-1", "us-west-1"]
```

| `from` | Locations |
| --- | --- |
| `Backends` | Each location where the backend's Instances run. This is the default. |
| `All` | Every location where NLBs are available. |
| `Names` | The locations in `names`. |

An address only serves traffic in a location where the backend has a healthy Instance, because traffic to a location's address goes only to Instances in that location. A location with an address and no Instances has nothing to send traffic to.

With the default, an address request gets an address only once a route attaches to its listener and the route's network service has Instances. Until then, the NLB reports `AllocationPending`.

NLB addresses are available in `us-central-1`, `us-east-1`, and `us-west-1`, the locations where Compute runs. `datumctl apply` accepts other location names in `names`, and the NLB then reports `AllocationPending` with the message `no pool offers this class`.

## Find the addresses and hostnames

Each entry in the NLB's `status.endpoints` describes one address request in one location:

```bash
datumctl get networkloadbalancer NLB_NAME -o yaml
```

```yaml
status:
  endpoints:
    - requestName: tcp-5432
      location: us-central-1
      canonicalHostname: us-central-1.lively-otter-x7k2p.datumproxy.net
      addresses:
        - family: IPv6
          value: 2001:db8:10c:1000::5
          announced: true
          dnsPublished: true
```

For what each field means, see [Addresses in each location](/nlb/observability#addresses-in-each-location).

To list only the hostnames, run the following command:

```bash
datumctl get networkloadbalancer NLB_NAME \
  -o jsonpath='{range .status.endpoints[*]}{.location}{"\t"}{.requestName}{"\t"}{.canonicalHostname}{"\n"}{end}'
```

In the [Cloud Portal](https://cloud.datum.net), the NLB's page lists the same addresses and hostnames, with a copy button for each.

## Generated hostnames

A generated hostname has the form `<location>.<label>.datumproxy.net`, such as `us-central-1.lively-otter-x7k2p.datumproxy.net`. The label is unique to the address request. Datum publishes an `AAAA` record for it with a 60-second time to live (TTL).

Keep the following points in mind:

- **One hostname for each location.** There's no single hostname that sends clients to the nearest location. Clients connect to a specific location's hostname. To spread clients across locations, publish several of them, or use DNS that you control.
- **A hostname doesn't carry a port.** Clients still connect to the listener's port, such as `us-central-1.lively-otter-x7k2p.datumproxy.net:5432`.
- **A hostname can resolve when it doesn't serve.** Datum publishes the DNS record as soon as it allocates the address, which can be before any Instance passes its health check. The record also stays while a location has no healthy Instance. A client that resolves the name then gets no answer. Check the NLB's `Ready` condition before you send traffic. See [Check that an NLB is serving](/nlb/operations#check-that-an-nlb-is-serving).
- **Hostnames and addresses last as long as the address request.** They stay the same when you change the NLB's routes or redeploy the workload. If you delete the address request or the NLB, Datum releases them and removes the DNS record within about 30 seconds. A new NLB gets a different hostname and address.

## Use your own domain

To serve an NLB on a domain that you own, such as `db.example.com`, create a `CNAME` record that points at the generated hostname of a location:

```text
db.example.com.  CNAME  us-central-1.lively-otter-x7k2p.datumproxy.net.
```

Clients then connect to `db.example.com` on the listener's port, and the record sends them to that one location.

A `CNAME` can't be at the apex of a zone, such as `example.com`. If Datum hosts the domain's DNS, use an `ALIAS` record at the apex. With another DNS provider, use its `ALIAS` or flattening record if it has one. Otherwise, create an `AAAA` record with the location's address. An `AAAA` record doesn't follow the address if it changes, so update it if you recreate the NLB.

Unlike an [Application Load Balancer](/alb/overview), an NLB doesn't need your domain added to it, and it doesn't issue a certificate for it. Clients that use TLS, such as `psql` with `sslmode=verify-full`, check the certificate that your workload presents, so the certificate must cover your domain.

### With Datum DNS

When Datum hosts your domain's DNS, use the `datumctl dns` plugin. To install it, run `datumctl plugin install dns`. If your DNS is hosted somewhere else, create the record at your own DNS provider instead.

<Steps>
  <Step title="Find the NLB's hostname">
    Pick the hostname for the location and listener that you want. See [Find the addresses and hostnames](#find-the-addresses-and-hostnames). The NLB must be ready first. See [Check that an NLB is serving](/nlb/operations#check-that-an-nlb-is-serving).
  </Step>
  <Step title="Create the zone, if you haven't already">
    ```bash
    datumctl dns zone create example.com
    ```

    Then point your domain at Datum's nameservers. See [Point your domain at Datum](/domain-dns/operations#point-your-domain-at-datum).
  </Step>
  <Step title="Add the record">
    ```bash
    datumctl dns record set example.com db CNAME GENERATED_HOSTNAME.
    ```

    Replace `GENERATED_HOSTNAME` with the NLB's hostname, and keep the trailing dot.

    To use the apex, `example.com`, create an `ALIAS` record instead, because a `CNAME` isn't allowed at the apex. See [ALIAS](/domain-dns/dns#alias-/-cname-flattening).

    ```bash
    datumctl dns record set example.com @ ALIAS GENERATED_HOSTNAME.
    ```
  </Step>
  <Step title="Check that it works">
    ```bash
    datumctl dns record list example.com --type CNAME,ALIAS
    dig +short AAAA db.example.com
    ```

    The record is live when its status is `Programmed`. `dig` returns the NLB's IPv6 address for that location.
  </Step>
</Steps>

To create the same records with `DNSZone` and `DNSRecordSet` manifests, follow [Point a domain with manifests](/domain-dns/point-to-alb#point-a-domain-with-manifests), and use the NLB's hostname as `TARGET`.

## Add a listener

In the Cloud Portal, open the NLB, and click **Add listener** in the listeners table.

With manifests, a new listener needs three things: a port on the network service that no other route uses, an address request and a listener on the NLB, and a route between them. The following example adds a UDP game server on public port `7777` to an NLB named `game-nlb`. It uses the `game` network service from [Health check a UDP service](/nlb/health-checks#health-check-a-udp-service), which has a UDP port named `game` and a TCP port named `health`:

1. Make sure that the network service has a port for the new listener. For a UDP listener, it also needs a TCP port for health checks. See [Network services](/galactic-vpc/networks/network-services).
2. Add an address request and a listener to the NLB. In early access, each listener needs its own address request, so the new listener gets its own IPv6 address and hostname:

   ```yaml
   spec:
     exposure:
       addresses:
         # ...existing address requests...
         - name: udp-7777
           families: ["IPv6"]
     listeners:
       # ...existing listeners...
       - name: udp-7777
         protocol: UDP
         port: 7777
         addressRefs: ["udp-7777"]
   ```

3. Create a route for the new listener:

   ```yaml
   apiVersion: networking.datumapis.com/v1alpha
   kind: NetworkLoadBalancerRoute
   metadata:
     name: game-nlb-udp-7777
   spec:
     parentRefs:
       - name: game-nlb
         listener: udp-7777
     backends:
       - networkService:
           name: game
           port: game        # UDP 7777
         healthCheck:
           protocol: TCP
           port: health      # TCP 8080
   ```

4. Apply both, and check that the NLB is `Ready`. See [Check that an NLB is serving](/nlb/operations#check-that-an-nlb-is-serving).

The existing listeners' addresses and hostnames don't change. If the new route sends traffic to a port that another route already uses, it reports `BackendClaimConflict`, and the NLB stops being `Ready`, although the existing listeners keep serving.

## Change where a listener sends traffic

This section and the next use the `echo-nlb` example from [Operations](/nlb/operations).

Edit the route's `backends`, and apply it again. You can change the network service, its port, or the health check port. To edit the route in place, run the following command:

```bash
datumctl edit networkloadbalancerroute echo-nlb-tcp-7000
```

The change reaches each location within seconds. New connections go to the new backend. To move traffic to a new version of your app without a new route, deploy the new version to the same workload instead.

## Remove a listener

In the Cloud Portal, delete the listener from the listeners table. An NLB needs at least one listener, so to remove the last one, delete the NLB.

With a manifest, delete the listener's route, and then remove the listener and its address request from the NLB, and apply it. Datum releases the listener's address and removes its DNS record within about 15 seconds. Resolvers that cached the record keep it for up to 60 seconds. `READY` can show `False` for a few seconds after the change.
