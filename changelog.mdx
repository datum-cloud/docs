<Update label="November 21, 2026" description="Network Load Balancer" tags={["AX/DX/UX", "Early access"]}>
  ## See your NLB traffic in the portal

  The [Cloud Portal](https://cloud.datum.net) now charts the inbound traffic each network load balancer receives, on the NLB page and on your project home.

  - **Metrics tab:** each NLB page has a Metrics tab with inbound throughput, packets, dropped packets, and backends, one line per listener and per region. Filter by region or listener, pick a time range, and drag across a chart to zoom in.
  - **Overview chart:** the "Connection metrics are coming soon" placeholder on the NLB overview is now a chart of the last hour of inbound throughput. Drag across it to open the Metrics tab on that window.

  NLBs are early access. See [Network services](/galactic-vpc/networks/network-services).

  Details: [Show NLB traffic metrics](https://github.com/datum-cloud/network-services-operator/issues/805) (#805), [Show network load balancer traffic on the project home](https://github.com/datum-cloud/cloud-portal/issues/1832) (#1832)

<Update label="November 19, 2026" description="Application Load Balancer" tags={["Fix"]}>
  ## Streaming responses stay open for up to an hour

  Load balancer responses are no longer cut off after about 15 seconds, so streams, large downloads, and slow APIs can finish.

  - **Before:** every response through the edge was cut at about 15 seconds, including Server-Sent Events, streaming tool calls, and downloads through tunnels. Raising the limit took a separate traffic policy aimed at a route you never created.
  - **Now:** each proxy rule has a request timeout that defaults to one hour. In testing, a 20-second streaming response completed through the edge with the default.
  - **Set it per rule:** give a rule its own `timeouts.request` to cut slow responses sooner. A rule timeout overrides a `BackendTrafficPolicy` request timeout.
  - **Clear errors:** a timeout of zero or above the platform maximum is refused when you apply it, with a message naming the field and the limit.

  See [How long a response can stay open](/alb/request-handling#how-long-a-response-can-stay-open).

  Details: [Streaming responses are cut off after fifteen seconds](https://github.com/datum-cloud/network-services-operator/issues/459) (#459)
</Update>

<Update label="November 18, 2026" description="datumctl" tags={["AX/DX/UX"]}>
  ## Five plugins move to the Milo catalog

  The `assistant`, `billing`, `ipam`, `search`, and `telemetry` plugins are now maintained in the Milo catalog, and datumctl v0.25.0 and later tells you how to switch.

  - **Warnings that name the replacement:** installing or upgrading one of these plugins from the datum catalog prints a deprecation warning with the commands to switch to the Milo catalog. The install or upgrade still completes.
  - **Nothing breaks yet:** older datumctl versions keep installing and upgrading these plugins from the datum catalog with no warnings. The datum catalog entries will be removed later, so switch before then.
  - **Same plugin name after you switch:** once you add the Milo catalog, installing a plugin by its bare name, such as `search`, picks the Milo replacement instead of reporting a name collision.
  - **Deprecated plugins stand out:** `datumctl plugin list`, `search`, and `browse` mark deprecated plugins and show their notice.
  - **No new installs of moved plugins:** `datumctl plugin install --all-available` skips a deprecated plugin you haven't installed.

  See [Deprecated plugins](/datumctl/plugins/using-plugins#deprecated-plugins).

  Details: [Support deprecating a catalog plugin in favor of another](https://github.com/datum-cloud/datumctl/issues/355) (#355), [Point the Milo plugin entries at the Milo catalog](https://github.com/datum-cloud/datumctl-plugins/issues/266) (#266)
</Update>

<Update label="November 13, 2026" description="gVPC" tags={["Fix"]}>
  ## Fewer network dropouts for instances

  Instances on a gVPC network keep their internet access and DNS lookups through two failures that used to interrupt them.

  - **No repeated egress blackouts:** replies from the internet to an instance could be dropped for several seconds at a time, over and over, while every component reported healthy. DNS lookups to public resolvers timed out and other internet traffic stalled. Datum now delivers those replies while it relearns the route back to the instance.
  - **Moved instances keep DNS:** when an instance was recreated on a different host, its DNS lookups could be denied for minutes. Datum now removes the old host's record of the instance when the instance stops there.

  See [gVPC troubleshooting](/galactic-vpc/troubleshooting).

  Details: [NAT replies to a tenant node drop for seconds when the kernel collects its next hop's neighbor entry](https://github.com/datum-cloud/galactic/issues/1392) (#1392), [Attachment status flips between nodes after an instance moves, dropping its routes](https://github.com/datum-cloud/galactic/issues/1385) (#1385)
</Update>

<Update label="November 11, 2026" description="Private DNS" tags={["Fix", "Early access"]}>
  ## Private DNS is faster and more reliable

  Instances can look up names in their own VPC through a private zone, and answers stay current as instances come and go.

  - **Answers follow your instances:** when an instance is deleted, its old answers disappear within 1 to 2 seconds. A replacement's new address answers about 4 seconds after the instance is ready. Answers are cached for 30 seconds.
  - **First lookup answers right away:** new instances get an answer to their first lookup immediately. Before, DNS gave no answer for 0 to 11 seconds after a deploy or restart, and apps that looked up a name at startup failed with `Temporary failure in name resolution`.
  - **No failed lookups during rollouts:** DNS stays up through platform restarts, software updates and edge reboots, because servers drain traffic before they stop. Before, a single rollout caused about 75 seconds of failed lookups. Staging rollouts with steady lookups now lose none.
  - **Several servers per resolver address:** several healthy DNS servers share one resolver address, with health checks, in all three regions. A lost host or edge affects only the instances on that host. Requests to a server on another host now get replies instead of timing out.
  - **Status you can trust:** zone status shows within seconds whether your records are being served.
  - **Isolation between VPCs:** each VPC's answers are isolated from every other VPC. Removing a zone from a VPC returns `NXDOMAIN`, and deleting a VPC withdraws its access from every DNS server. Only the platform can change which DNS a VPC uses.

  Private DNS is in preview. See [Private DNS](/domain-dns/private-dns).

  Details: [Keep Private DNS working through updates and failures](https://github.com/datum-cloud/dns-operator/issues/417) (#417), [Keep private DNS records up to date](https://github.com/datum-cloud/dns-operator/issues/415) (#415), [Restrict private DNS access to approved networks](https://github.com/datum-cloud/dns-operator/issues/416) (#416)
</Update>

<Update label="November 6, 2026" description="datumctl" tags={["AX/DX/UX"]}>
  ## Set up datumctl from a coding agent

  Coding agents and scripts can now sign in and install plugins without an interactive terminal.

  - **Fixed:** installing a plugin from a GitHub repository that publishes only pre-releases now installs the newest pre-release.
  - **Fixed:** listing a resource across all namespaces at organization scope now explains why it's refused and how to list across a project instead. Passing `<org>/<project>` as a project name fails right away with a hint naming the bare project.

  See [Logging in](/datumctl/auth/logging-in) and [Using plugins](/datumctl/plugins/using-plugins).

  ## Run gRPC APIs on Datum

  The Application Load Balancer now supports HTTP/2 from clients to origins, so gRPC APIs can run on Datum and be called at their ALB hostname.

<Update label="October 7, 2026" description="Application Load Balancer" tags={["Deliver", "Early access"]}>
  ## Wildcard hostnames

  An Application Load Balancer can now serve every subdomain of a domain you own. Add a hostname such as `*.example.com` and get one automatically issued and renewed certificate that covers all names one level below the domain.

  ```bash
  datumctl alb hostname add my-app '*.example.com'
  datumctl alb describe my-app
  ```

  Publish the `_acme-challenge` CNAME record that `describe` shows. The certificate is typically issued within a few minutes, and the record stays the same at renewal.

  This is an early-access capability that isn't turned on by default, so contact Datum to enable it for your project. It requires the alb plugin v0.32.3 or later (`datumctl plugin upgrade alb`). A wildcard matches one label level only: `*.example.com` covers `app.example.com` but not `a.b.example.com`.

  [Read the announcement](https://github.com/orgs/datum-cloud/discussions/303)
</Update>
