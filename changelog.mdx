<Update label="November 10, 2026" description="Application Load Balancer" tags={["AX/DX/UX"]}>
  ## Shareable log views with filter counts

  The **Logs** tab of a load balancer in the [Cloud Portal](https://cloud.datum.net) keeps your view when you refresh or share it.

  - **Links keep the view:** the time range, filters, search, live mode, and the open row are saved in the page URL. Refreshing a preset window such as the last 30 minutes moves it up to now.
  - **Filters cover the whole window:** filter options come from every log line in the time range, not just the rows loaded on screen. Selecting one option no longer hides the others.
  - **Counts per option:** each filter option shows how many lines match your other selected filters. Counts are hidden while you search, and method and status code counts are hidden while a host is selected.
  - **Host filter matches the table:** the **Host** filter lists the same host each row shows in the **Host** column.
  - **No flash on filter clicks:** earlier rows stay on screen while new results load.

  See [Access logs](/alb/observability#access-logs).
</Update>

<Update label="November 6, 2026" description="datumctl" tags={["AX/DX/UX"]}>
  ## Set up datumctl from a coding agent

  Coding agents and scripts can now sign in and install plugins without an interactive terminal.

  - **Pick a context at login:** `datumctl login` reads `--project`, `--organization`, `DATUM_PROJECT`, and `DATUM_ORGANIZATION` to choose the context without the picker. `--project` also accepts `<org>/<project>`.
  - **Login without a terminal:** when no context is named, `datumctl login` saves your session, leaves the context unset, and tells you to run `datumctl ctx use <org>/<project>`.
  - **Switching accounts:** signing in with a different account clears a context that belongs to the other account, so the new account becomes active.
  - **Install every plugin:** `datumctl plugin install --all-available` installs or upgrades every plugin in the official `datum` catalog, or the catalog named by `--index`. Third-party catalogs ask for confirmation first. Pass `--yes` to skip it.
  - **Scriptable search:** `datumctl plugin search -o json` prints an array of plugins, and `-o name` prints one plugin name per line.
  - **Fixed:** installing a plugin from a GitHub repository that publishes only pre-releases now installs the newest pre-release.
  - **Fixed:** listing a resource across all namespaces at organization scope now explains why it's refused and how to list across a project instead. Passing `<org>/<project>` as a project name fails right away with a hint naming the bare project.

  See [Logging in](/datumctl/auth/logging-in) and [Using plugins](/datumctl/plugins/using-plugins).
</Update>

  Networks in the [Cloud Portal](https://cloud.datum.net) now have a **Metrics** tab that charts traffic in and out for every Instance attached to the network.

  - The **Overview** tab shows a 30-minute traffic chart for each Instance that opens it on the **Metrics** tab.
  - Networks with more than 100 interfaces now list all of them.

  See [gVPC observability](/galactic-vpc/observability).
</Update>

<Update label="November 5, 2026" description="Billing" tags={["AX/DX/UX"]}>
  ## See your contract in billing settings

  If your billing account is on a contract, the [Cloud Portal](https://cloud.datum.net) now shows it in a **Contract** section on the billing account page.

  - **Contract details:** the start date in UTC, an **Active** or **Upcoming** badge, the billing day, whether usage is billed on top, and the fixed fees before discounts.
  - **Fee amounts:** each fee shows its total, and fees with a quantity or unit show how they add up, for example "4 × $300 / port".
  - **Billing cycles follow the contract:** once a contract starts, payment terms and the [Usage](/organizations/usage) page use its billing day. Before it starts, the billing cycle says when the contract's day takes over.
  - **End-of-month days:** a billing cycle on the 29th to 31st returns to that day after a shorter month.
  - **Billing accounts list:** long project names are shortened with the full name on hover, and accounts on payment terms show **Invoice** as their payment method.

  See [Contracts](/organizations/billing#contracts).
</Update>

<Update label="November 5, 2026" description="Private DNS" tags={["Fix", "Early access"]}>
  ## Clearer limits and labels for private zones

  - **Zone limit enforced:** a network can have up to 256 private zones, including its managed `datum.internal` zone. An association past the limit now reports `Accepted=False` with reason `ZoneLimitExceeded`, instead of being accepted and stopping the network from picking up zone changes.
  - Zones already attached keep their place, and the managed zone always fits. Associating the same zone twice uses one slot.
  - **Portal:** the DNS list shows **Private** in the **Host** column for private zones instead of a lookup that never finishes, and the zone page hides the **Nameservers** tab for them.
  - Each network's managed zone is described as "Private DNS for the `<network>` VPC", so you can tell which network a zone serves.

  Private DNS is in preview. See [Private DNS](/domain-dns/private-dns).
</Update>

<Update label="October 30, 2026" description="Private DNS" tags={["Early access", "Connect"]}>
  ## Private DNS for gVPC networks

  Resources on a [gVPC](/galactic-vpc/overview) network can now reach each other by name, with answers that resolve only from inside that network.

  - **Managed zone:** every network gets its own `datum.internal` zone. Compute publishes each Instance at `<instance-name>.instances.datum.internal`. See [Private DNS for Compute](/compute/private-dns).
  - **Your own private zones:** associate private zones with a network for internal names. The zone class is now optional for private zones.
  - **Network isolation:** a network can't be pointed at another network's private DNS, and the same names can be reused across networks without leaking answers.
  - **Availability:** lookups go only to healthy DNS servers, so server updates no longer stall lookups until they time out.
  - **Regions:** a private zone is served only in the regions its networks use, and is withdrawn from regions it leaves.
  - **Fixed:** a CNAME that points into another private zone now returns the target's answer over UDP, not just the CNAME.
  - **Fixed:** the managed `datum.internal` zone can't be deleted while its network uses it. Deleting a project still removes it.
  - **Changed:** the DNS Admin role can no longer create service-owned name registrations or naming policies. It keeps read access.

  Private DNS is in preview, and Instances have IPv6 addresses only. Learn more in [Private DNS](/domain-dns/private-dns).
</Update>

<Update label="October 30, 2026" description="Network Load Balancer" tags={["Connect", "Early access"]}>
  ## Network load balancers

  Publish a network service on a public TCP or UDP port with a network load balancer (NLB).

  - **Addresses and hostnames:** each location gets a public IPv6 address and a generated hostname you can point a CNAME at. IPv4 is available for single-port listeners where Datum has enabled it.
  - **Health checks:** NLBs actively check backends and send new connections only to healthy ones.
  - **UDP ports:** network services now accept UDP ports, and the create-service dialog has a TCP/UDP selector per port. A UDP listener also needs a TCP port on the backend for its health check.
  - **Portal:** create an NLB, copy its hostname and address, and add, edit, or delete listeners in the [Cloud Portal](https://cloud.datum.net).

  NLBs are early access. TLS listeners aren't supported yet, but a TCP listener forwards TLS traffic unchanged to your backend. Each route serves one backend. An ALB that points at a UDP port now reports a clear unsupported-protocol error.

  See [Network services](/galactic-vpc/networks/network-services).
</Update>

<Update label="October 21, 2026" description="Application Load Balancer" tags={["Build", "Connect"]}>
  ## Run gRPC APIs on Datum

  The Application Load Balancer now supports HTTP/2 from clients to origins, so gRPC APIs can run on Datum and be called at their ALB hostname.

  - **Compute:** add `--http2` at deploy time to prepare the workload's ALB for gRPC clients. The setting persists across later deploys. Requires the compute plugin v0.12.11 or later.
  - **Network services:** mark a service port as HTTP/2 so any ALB using that port can serve gRPC. Requires the network and alb plugins v0.32.26 or later.
  - **Hostnames:** generated and custom hostnames both support HTTP/2. HTTP/1.1 clients are unaffected.
  - **TLS:** the ALB terminates TLS, so your server speaks plain gRPC.

  Origins added by URL, including servers outside Datum, still use HTTP/1.1. If your app uses WebSockets, serve them on a separate port without HTTP/2.

  [Read the announcement](https://github.com/orgs/datum-cloud/discussions/310)
</Update>

<Update label="October 7, 2026" description="Application Load Balancer" tags={["Deliver", "Early access"]}>
  ## Wildcard hostnames

  An Application Load Balancer can now serve every subdomain of a domain you own. Add a hostname such as `*.example.com` and get one automatically issued and renewed certificate that covers all names one level below the domain.

  ```bash
  datumctl alb hostname add my-app '*.example.com'
  datumctl alb describe my-app
  ```

  Publish the `_acme-challenge` CNAME record that `describe` shows. The certificate is typically issued within a few minutes, and the record stays the same at renewal.

  This is an early-access capability that isn't turned on by default, so contact Datum to enable it for your project. It requires the alb plugin v0.32.3 or later (`datumctl plugin upgrade alb`). A wildcard matches one label level only: `*.example.com` covers `app.example.com` but not `a.b.example.com`.

  [Read the announcement](https://github.com/orgs/datum-cloud/discussions/303)
</Update>

<Update label="September 29, 2026" description="Patch" tags={["AX/DX/UX"]}>
  ## Patch can work with your compute, DNS, and load balancing

  Patch can now query Compute, DNS, and Application Load Balancer data directly, so troubleshooting follows the actual cause instead of inferring it from generic resource reads.

  - **Compute:** follows top-level reasons such as `Available=False` with `QuotaNotGranted` down to the instance-level condition that holds the cause.
  - **DNS:** diagnoses zones, records, and delegation, including domain verification, conflicting records, and zone imports.
  - **Load balancing:** covers certificates, unreachable backends, edge propagation, and access logs.

  The service tools are read-only. Any change goes through a plan you review and approve. Which tools are available depends on what each project is entitled to.

  In the terminal, run `datumctl assistant` for a full-screen chat, `datumctl assistant chat "..."` for a one-shot answer in scripts, or `datumctl assistant resume` to search project conversations. Install it with `datumctl plugin install assistant`.

  [Read the announcement](https://github.com/orgs/datum-cloud/discussions/300)
</Update>
