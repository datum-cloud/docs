<Update label="November 25, 2026" description="Application Load Balancer" tags={["Fix"]}>
  ## Load balancers refuse unsafe settings

  The Application Load Balancer (ALB) now refuses settings it used to accept and then mishandle.

  - **Public origins only:** an origin on a private or internal address is refused, and the message names the value.
  - **Connectors still reach private networks:** a proxy that tunnels through a connector still reaches private addresses on your side.
  - **Existing ALBs keep serving:** stored origins are not re-checked, but the next edit is refused until you replace a private origin.
  - **Health checks stay on:** a policy that would replace the health checks Datum sets for the ALB is refused. One attached earlier shows as not applied.

  See [Load balancing and health checks](/alb/configuration/load-balancing).

  Details: [Health checks silently stop when a customer adds a route timeout policy](https://github.com/datum-cloud/network-services-operator/issues/880) (#880), [Refuse internal addresses in tenant upstreams](https://github.com/datum-cloud/network-services-operator/pull/956) (#956)
</Update>

<Update label="November 20, 2026" description="Application Load Balancer" tags={["Fix"]}>
  ## Responses stay open for up to an hour

  The Application Load Balancer (ALB) no longer cuts responses off after about 15 seconds. Streams, Server-Sent Events, large downloads, and slow APIs can now finish.

  - **One-hour default:** each proxy rule has a request timeout that defaults to one hour, and a 20-second streaming response completed with it in testing.
  - **Per-rule timeouts:** set `timeouts.request` on a rule to cut slow responses sooner, and it overrides a `BackendTrafficPolicy` request timeout.
  - **Checked on apply:** a timeout of zero or above the platform maximum is refused with a message naming the field and the limit.

  See [How long a response can stay open](/alb/request-handling#how-long-a-response-can-stay-open).

  Details: [Streaming responses are cut off after fifteen seconds](https://github.com/datum-cloud/network-services-operator/issues/459) (#459)
</Update>

  The `datumctl dns` plugin no longer guesses when several zones share a domain, so a record can't land in another VPC's zone.

  Deleting a private zone asks you to confirm with its object name. Projects where each domain has one zone see no change.

<Update label="November 10, 2026" description="Private DNS" tags={["Fix", "Early access"]}>
  ## Private DNS answers faster and stays up

  Private DNS now keeps answers current as instances come and go, and keeps answering through rollouts and failures.

  - **Current answers:** a deleted instance's answers disappear within 1 to 2 seconds, and a replacement answers about 4 seconds after it's ready, and answers are cached for 30 seconds.
  - **Immediate first lookups:** new instances get an answer right away, where lookups used to fail for up to 11 seconds after a deploy or restart.
  - **Up through rollouts:** servers drain before they stop, so staging rollouts lose no lookups instead of about 75 seconds of failures.
  - **Isolation between VPCs:** each VPC's answers are isolated from every other VPC, and removing a zone from a VPC returns `NXDOMAIN`.

  Several healthy DNS servers share one resolver address in all three regions, so a lost host or edge affects only the instances on that host. Deleting a VPC withdraws its access from every DNS server, and only the platform can change which DNS a VPC uses. Zone status shows within seconds whether your records are being served. Private DNS is in preview. See [Private DNS](/domain-dns/private-dns).

  Details: [Keep Private DNS working through updates and failures](https://github.com/datum-cloud/dns-operator/issues/417) (#417), [Keep private DNS records up to date](https://github.com/datum-cloud/dns-operator/issues/415) (#415), [Restrict private DNS access to approved networks](https://github.com/datum-cloud/dns-operator/issues/416) (#416)
</Update>

<Update label="November 10, 2026" description="Private DNS" tags={["Early access", "Connect"]}>
  ## Private DNS for Galactic VPC networks

  Resources on a [Galactic VPC](/galactic-vpc/overview) network can now reach each other by name, with answers that resolve only from inside that network.

  - **Managed zone:** every network gets its own `datum.internal` zone, and Compute publishes each Instance at `<instance-name>.instances.datum.internal`.
  - **Your own private zones:** associate private zones with a network for internal names.
  - **Network isolation:** a network can't use another network's private DNS, and the same names can be reused across networks without leaking answers.
  - **Regions:** a private zone is served only in the regions its networks use, and is withdrawn from regions it leaves.
  - **Healthy servers only:** lookups go only to healthy DNS servers, so server updates no longer stall lookups until they time out.

  Private DNS is in preview, and Instances have IPv6 addresses only. The managed `datum.internal` zone can't be deleted while its network uses it, though deleting the project still removes it. A CNAME that points into another private zone now returns the target's answer over UDP. The DNS Admin role can no longer create service-owned name registrations or naming policies, and keeps read access.

  See [Private DNS](/domain-dns/private-dns) and [Private DNS for Compute](/compute/private-dns).

  Details: [Manage Private DNS through the API](https://github.com/datum-cloud/dns-operator/issues/414) (#414), [Keep private DNS records up to date](https://github.com/datum-cloud/dns-operator/issues/415) (#415), [Restrict private DNS access to approved networks](https://github.com/datum-cloud/dns-operator/issues/416) (#416)

<Update label="November 3, 2026" description="Network Load Balancer" tags={["Connect", "Early access"]}>
  ## Network Load Balancer for TCP and UDP

  A Network Load Balancer (NLB) now publishes a network service on a public TCP or UDP port.

  - **Addresses and hostnames:** each location gets a public IPv6 address and a generated hostname you can point a CNAME at, and IPv4 is available for single-port listeners where Datum has enabled it.
  - **Health checks:** NLBs check backends and send new connections only to healthy ones.
  - **UDP ports:** network services accept UDP ports with a TCP/UDP selector per port in the create-service dialog, and a UDP listener also needs a TCP port on the backend for its health check.
  - **Portal:** create an NLB, copy its hostname and address, and manage listeners in the [Cloud Portal](https://cloud.datum.net).

  NLBs are early access. TLS listeners are not supported yet, but a TCP listener forwards TLS traffic unchanged to your backend. Each route serves one backend. An ALB that points at a UDP port now reports a clear unsupported-protocol error.

  See [Network services](/galactic-vpc/networks/network-services).

<Update label="October 19, 2026" description="Application Load Balancer" tags={["Build", "Connect"]}>
  ## gRPC APIs on Datum

  The Application Load Balancer (ALB) now supports HTTP/2 from clients to origins, so you can run gRPC APIs on Datum and call them at their ALB hostname.

  - **Compute:** add `--http2` at deploy time to prepare the workload's ALB for gRPC, with the compute plugin v0.12.11 or later.
  - **Network services:** mark a service port as HTTP/2 so any ALB using it can serve gRPC, with the network and alb plugins v0.32.26 or later.
  - **TLS at the edge:** the ALB terminates TLS on generated and custom hostnames, so your server speaks plain gRPC and HTTP/1.1 clients are unaffected.

  Origins added by URL, including servers outside Datum, still use HTTP/1.1. The `--http2` setting persists across later deploys. Serve WebSockets on a separate port without HTTP/2.

  See [gRPC to your origin](/alb/request-handling#grpc-to-your-origin).

<Update label="October 7, 2026" description="Application Load Balancer" tags={["Deliver", "Early access"]}>
  ## Wildcard hostnames

  An Application Load Balancer (ALB) can now serve every subdomain of a domain you own. Add a hostname such as `*.example.com` to get one automatically issued and renewed certificate for all names one level below it.

  ```bash
  datumctl alb hostname add my-app '*.example.com'
  datumctl alb describe my-app
  ```

  Publish the `_acme-challenge` CNAME record that `describe` shows, and the certificate is typically issued within a few minutes. The record stays the same at renewal. Wildcard hostnames are early access and off by default, so contact Datum to enable them for your project. They require the alb plugin v0.32.3 or later (`datumctl plugin upgrade alb`). A wildcard matches one label level only: `*.example.com` covers `app.example.com` but not `a.b.example.com`.

  See [Wildcard hostnames](/alb/configuration/wildcard-hostnames).

  [Read the announcement](https://github.com/orgs/datum-cloud/discussions/303)
</Update>
