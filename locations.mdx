Datum’s infrastructure footprint is organized into points of presence (PoPs) that are packaged into Regions and Availability Zones (AZs). For a visual overview of all PoPs, see the [Locations](https://www.datum.net/locations/) page.

Each Region represents a specific geographic and network boundary, while each AZ provides independent capacity within that Region. This structure supports predictable latency, fault isolation, and regulatory alignment.

## Why a region is a real place

Some clouds hide location behind a single global network, which is simple but leaves you unable to answer basic questions: which city is my traffic and data actually passing through? What laws apply to it? How far away is it from my users?

Datum takes the opposite approach: every Region and Availability Zone corresponds to an actual, named place, not an abstract label. When you deploy into `us-east-1`, that's a real facility in Ashburn, Virginia. It isn't a logical construct spread invisibly across a continent. This gives you three things:

- **Predictable latency**: Datum groups Regions by real network distance, so you can reason about how fast your app responds to users in a given area.
- **Data location**: because each Region maps to a specific country, you can reason about which jurisdiction your workloads run in. Regulatory and export-control requirements can still limit where a workload may run, and they take precedence over the placement rules below.
- **Real choice and control**: you pick where things run based on your own requirements, such as proximity to users, legal residency, or avoiding a single point of failure. You choose the same way you would between physical data centers, rather than accepting one big undifferentiated "everywhere."

Most customers pick a Region close to their users or their required jurisdiction. To add redundancy, or to serve users in more than one part of the world, deploy to more than one Region. To see which Regions your project can use today, see [Check what's available to your project](#check-what’s-available-to-your-project).

## Naming convention

Similar to the large public clouds, Datum uses a country-anchored naming format with the following elements:

| **Field** | **Description** |
| --- | --- |
| Geography | Two-letter ISO country code (example: US, DE, IN) |
| Cardinal direction | Directional indicator within the country: north, south, east, west, or central. |
| Number | Region index within that location. |
| Count | Availability Zone identifier: a, b, c, etc. |

Anchoring to a two-letter country code, rather than a continent, means a region name never leaves you guessing which country it's in. For example, an "east" region is always clearly in a specific country. You won't confuse a US region with a Canadian one, as you might with a broader label like "North America."

For example, here is how Datum names the first region and availability zone in the eastern US.

```text
<Geography>-<Location>-<Number><Count>
```

`Example: us-east-1a`

Distance and policy boundaries define Regions and AZs.

- When PoPs in the same country are separated by more than about 5 milliseconds round-trip time (RTT), Datum creates a new Region.
- If multiple PoPs exist in the same metro but operate independently (for example, separate network clusters or facilities), they become separate AZs. Datum increments the Count value to the next letter.
- If PoPs are within about 5 milliseconds RTT and part of the same operational domain, they remain in the same Region. Example: us-east-1a, us-east-1b, us-east-1c.

*Note: regulatory and export control requirements may restrict or define where data and workloads can reside. These boundaries take precedence over latency-based placement rules.*

## Check what's available to your project

The table above is Datum's global footprint. What you can deploy into is a narrower, per-project question. Datum represents each usable location as a `Location` resource, and offers you the ones inside your project's own control plane.

`datumctl get locations` lists them:

```bash
datumctl get locations --project your-project-id
```

```text
NAME           CLASS           CITY   AGE   READY   REASON
us-central-1   datum-managed   DFW    20h
us-east-1      datum-managed   IAD    20h
```

Each row is a location you can place work in today. `NAME` is the identifier you reference elsewhere, and matches the region codes in the table above: `us-central-1` is Dallas, `us-east-1` is Ashburn. `CITY` is the airport-style code for the metro it serves. `CLASS` is the kind of capacity behind it, where `datum-managed` is Datum's own footprint.

<Tip>
  This list reflects your active project scope. If a location you expect is missing, confirm you are pointed at the right project. See [Contexts & scoping](/datumctl/contexts-and-scoping).
</Tip>

For the full definition of a location, including its topology, request YAML or JSON:

```bash
datumctl get location us-central-1 --project your-project-id -o yaml
```

```yaml
apiVersion: locations.miloapis.com/v1alpha1
kind: Location
metadata:
  name: us-central-1
spec:
  locationClassRef:
    name: datum-managed
  topology:
    topology.datum.net/city-code: DFW
    topology.datum.net/region: us-central-1
```

## Region tracing

Visit [<u>https://edge.datum.net/</u>](https://edge.datum.net/) to learn which Datum Region and availability zone you're reaching via anycast. If you're using Datum Tunnels, this is your entry point into Datum's network.

You can also access Datum's zones and locations programmatically:

- JSON structured response [<u>https://edge.datum.net/api/edge-info</u>](https://edge.datum.net/api/edge-info)
- Plaintext [<u>https://edge.datum.net/api/trace</u>](https://edge.datum.net/api/trace)
