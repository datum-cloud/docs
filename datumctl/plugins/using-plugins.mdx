Plugins extend `datumctl` with additional commands without changing the core CLI. A plugin is an independent binary that datumctl runs on your behalf — once installed, you invoke it exactly like a built-in command. For the thinking behind plugins, see [Extending our CLI with plugins](https://www.datum.net/blog/extending-our-cli-with-plugins/) on the Datum blog.

<Info>
  Plugins are optional. You never need one to use `datumctl`, and the core CLI works the same whether or not you have any installed.
</Info>

## What a plugin is

When you install the `compute` plugin from the official **datum** catalog, its commands become available under `datumctl compute`:

```bash
datumctl compute --help
```

(See [Compute](/datumctl/compute/overview) for what that plugin does.)

datumctl injects your current organization, project, and a fresh short-lived access token into the plugin automatically, so plugins work with your [active context](/datumctl/contexts-and-scoping) and [credentials](/datumctl/auth/managing-accounts) without a separate login.

Plugins come from **catalogs** (also called indexes). The official **datum** catalog is curated by Datum and always available with no setup — its plugins carry an `official` trust badge. You can also add third-party catalogs, whose plugins carry a `third-party` badge. See [Adding catalogs](/datumctl/plugins/adding-catalogs) to register more.

## Finding plugins

Search every registered catalog for available plugins:

```bash
# List everything available across all catalogs
datumctl plugin search

# Filter by name or description
datumctl plugin search compute

# Scope the search to a single catalog
datumctl plugin search deploy --index acme
```

Results show the plugin name, the catalog it came from, its version, its trust badge, and a short description.

For scripts and coding agents, pass `-o json` or `-o name`. `-o json` prints an array of objects with `name`, `index`, `version`, `trust`, and `description` fields, or `[]` when nothing matches. A plugin its catalog marks deprecated also has a `deprecated` object with the catalog's `message` and `replacement`. `-o name` prints one plugin name per line:

```bash
datumctl plugin search --index datum -o json
datumctl plugin search -o name
```

Prefer to explore interactively? `plugin browse` opens a filterable picker where you can inspect a plugin's details and install it in place:

```bash
datumctl plugin browse
```

<Note>
  `plugin browse` requires an interactive terminal. In scripts or CI, use `plugin search` instead.
</Note>

## Installing a plugin

Datum's own plugins are documented with the products they manage. For example, see [DNS operations](/domain-dns/operations) for the `dns` plugin and [Compute commands](/datumctl/compute/overview) for the `compute` plugin.

Install by name from a catalog:

```bash
# Install from the official datum catalog (searched first)
datumctl plugin install compute

# Install from a specific catalog
datumctl plugin install acme/deploy
```

You can also install directly from a GitHub release, without a catalog:

```bash
# Latest release, or the newest pre-release if there's no stable one
datumctl plugin install your-org/datumctl-example

# A specific release
datumctl plugin install your-org/datumctl-example@v1.2.0
```

Without a version, datumctl installs the release GitHub marks as latest. If the repository has published only pre-releases, datumctl installs the highest pre-release instead, and `datumctl plugin upgrade` follows newer pre-releases the same way.

<Info>
  If a bare name exists in more than one catalog, datumctl lists the matches instead of guessing. Qualify the name with its catalog (for example `acme/deploy`) to choose. A deprecated plugin and its same-named replacement don't count as a collision; see [Deprecated plugins](#deprecated-plugins).
</Info>

### Pinning a version

Pin a specific version at install time by appending `@version`:

```bash
# Pin a catalog plugin
datumctl plugin install compute@v0.8.0-dev.7
datumctl plugin install acme/deploy@v2.0.0

# Pin a GitHub release
datumctl plugin install your-org/datumctl-example@v1.2.0
```

Without `@version`, datumctl installs the version the catalog recommends.

### Restoring your plugin set

Run `install` with no arguments to restore every plugin you previously installed, at its recorded version. This reproduces your plugin set on a new machine:

```bash
datumctl plugin install
```

## Listing what you have

```bash
datumctl plugin list
```

This shows each installed plugin with its catalog, version, trust badge, description, and a status indicator:

| Status       | Meaning                                             |
|--------------|-----------------------------------------------------|
| `ok`         | Installed and compatible with this datumctl.        |
| `update`     | A newer version is available in its catalog.        |
| `deprecated` | Its catalog marks the plugin deprecated. See [Deprecated plugins](#deprecated-plugins). |
| `!`          | Built for a different datumctl version.             |
| `?`          | Version information is unavailable.                 |

## Running an installed plugin

An installed plugin behaves like a native command:

```bash
datumctl compute --help
```

Tab completion works transparently — datumctl forwards completion requests to the plugin, so completing subcommands and flags just works:

```bash
datumctl compute <TAB>
```

## Upgrading and removing

```bash
# Upgrade a plugin to the latest version
datumctl plugin upgrade compute

# Remove a plugin
datumctl plugin remove compute
```

To upgrade every plugin you have installed at once, run `datumctl plugin upgrade --all`. `datumctl plugin list` shows `update` in the `STATUS` column for any plugin with a newer version.

`plugin upgrade` runs the same verified install flow as a fresh install.

### Deprecated plugins

When a catalog marks a plugin as deprecated, usually because it moved to another catalog, datumctl prints a warning when you install, restore, or upgrade that plugin. `plugin upgrade` prints it whether or not a newer version was installed. The install or upgrade still completes. The warning names the replacement and the commands to switch to it:

```text
warning: deploy is deprecated: deploy moved to the ACME Platform catalog.
  To switch to the replacement:
    datumctl plugin index add acme-platform acme-platform/datumctl-plugins
    datumctl plugin install acme-platform/deploy
```

If you already added the replacement's catalog, the warning shows only the `datumctl plugin install` line, using the name you gave that catalog. If your organization's policy disables that catalog, the warning says so instead of suggesting commands.

Run the suggested commands to switch. After `datumctl plugin install <catalog>/<name>`, datumctl records the plugin as installed from the new catalog, so `plugin upgrade` uses that catalog and the warning stops. Plugins installed directly from a GitHub release never show this warning.

After you add the replacement's catalog, a bare-name install such as `datumctl plugin install ipam` installs the replacement when it has the same name. datumctl doesn't report that the name exists in multiple catalogs. It first prints this note to stderr, once for each deprecated match it skips:

```text
note: <name> in <catalog> is deprecated; installing its replacement from <catalog>
```

If other catalogs also have a plugin with that name, the collision error lists only those catalogs and the replacement. A replacement with a different name isn't picked this way. Install it with `datumctl plugin install <catalog>/<new-name>`.

`datumctl plugin install --all-available` skips a deprecated plugin you haven't installed and prints `Skipped <name>: deprecated`. A deprecated plugin you already have is still upgraded, or reported as up to date, and datumctl prints its deprecation warning.

Listings flag deprecated plugins too:

- `datumctl plugin list` shows `deprecated` in the `STATUS` column in place of `update`. When a newer version also exists, datumctl still suggests `datumctl plugin upgrade`. A plugin built for a different datumctl version still shows `!`, and one without version information still shows `?`. After the table, datumctl prints the deprecation warning for each deprecated plugin to stderr, whatever its status. `plugin list` reads only the catalog indexes datumctl has cached, so run `datumctl plugin search` to refresh them.
- `datumctl plugin search` adds `[deprecated]` before the description and prints the warning for each deprecated result to stderr after the table. With `-o json`, each deprecated result carries a `deprecated` object instead. `-o json` and `-o name` print no warnings.
- `datumctl plugin browse` adds `(deprecated)` after the plugin name and shows the warning in the plugin's details.

The `assistant`, `billing`, `ipam`, `search`, and `telemetry` plugins have moved from the **datum** catalog to the [Milo catalog](https://github.com/milo-os/cli-plugins), and their **datum** entries are deprecated. They keep installing from the **datum** catalog until Datum removes them. datumctl v0.25.0 and later shows the deprecation warning for them. To switch a plugin, add the Milo catalog and install the plugin from it:

```bash
datumctl plugin index add milo-os milo-os/cli-plugins
datumctl plugin install milo-os/telemetry
```

## How plugins stay trustworthy

datumctl treats a plugin as untrusted code and protects you in a few ways:

- **HTTPS-only downloads.** Plugin archives and catalog manifests are fetched over HTTPS only. Downloads to private, loopback, or link-local addresses are refused, and redirects are re-checked on every hop.
- **Checksum verification on every run.** datumctl records a SHA256 fingerprint of each plugin binary at install time and verifies it *every time the plugin runs*. If a managed plugin binary is modified after installation, datumctl refuses to run it.
- **Trust badges.** Every plugin and catalog shows whether it is `official` (Datum's curated **datum** catalog) or `third-party`, so you always know the source.

<Warning>
  Third-party plugins are programs that run on your machine with your Datum credentials, and Datum does not review them. Only install plugins from catalogs and sources you trust. See [Adding catalogs](/datumctl/plugins/adding-catalogs) for the trust decision involved in registering a catalog.
</Warning>

### Trusting a plugin already on your PATH

If you have a plugin binary on your `PATH` that datumctl did not install (named `datumctl-<name>` or `milo-<name>`), datumctl blocks it from running until you explicitly trust it:

```bash
# Allow an unmanaged PATH plugin to run
datumctl plugin trust dns

# Revoke that trust later
datumctl plugin untrust dns
```

Trusting records the binary's path and fingerprint. If the binary changes afterward, datumctl blocks it again until you re-run `plugin trust`.
