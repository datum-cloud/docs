`datumctl compute` deploys a container image as a *workload* that runs in one or more Datum Cloud locations, and provides the day-to-day commands to scale, restart, and delete it. It's a first-party plugin instead of a built-in command. After you install it, its commands behave like the rest of the CLI.

```bash
datumctl plugin install compute
datumctl compute --help
```

<Info>
  New to plugins? [Using plugins](/datumctl/plugins/using-plugins) covers installation, upgrades, and how a plugin inherits your active context and credentials. Not installed `datumctl` itself yet? Start with [Install](/datumctl/install).
</Info>

## Core concepts

A handful of terms recur across every `compute` command:

| Term | Meaning |
|------|---------|
| **Workload** | The thing you deploy — a container image plus its runtime configuration (ports, env, instance type) and one or more [placements](/compute/placement-and-scaling). |
| **Placement** | A named group of locations and a scale policy (minimum replica count) in a workload. A flag-based `deploy` creates a single placement named `default`. |
| **Location** | A Datum Cloud region a workload can run in, for example `us-central-1`. The `--city` flag selects every location in a city by its code, such as `DFW`. |
| **Instance** | One running copy of a workload's container in one location. A placement with `--min=2` across two locations produces four Instances. |

`compute` is project-scoped: every command reads `--project` (or your active context's project, injected automatically — see [Contexts & scoping](/datumctl/contexts-and-scoping)). There is no organization-level view and no `--namespace` flag; all compute resources live in the project's `default` namespace.

## Enabling Compute

Compute is a self-service service: you don't request access, and no one at Datum reviews it. The first time you run a command that needs Compute, such as `deploy`, `workloads`, `instances`, or `build`, `datumctl` checks whether Compute is enabled for the project. If it isn't, `datumctl` enables it, waits a few seconds for it to become active, and then runs your command:

```bash
datumctl compute deploy api --image=ghcr.io/acme/api:1.4.2 --location=us-central-1 --min=1
```

`datumctl` doesn't prompt before it enables Compute, so the first command works the same way on a terminal, in CI, and in a script. Enabling Compute also gives the project its default compute quota.

### Checking access explicitly

To see whether Compute is enabled, or to enable it without running another command, use `datumctl compute access`:

```bash
# Show the current state
datumctl compute access

# Enable Compute for the project now
datumctl compute access request
```

`datumctl compute access` prints the service, the project, and an `Access` line with one of the following states:

| State | Meaning |
|-------|---------|
| `Not requested` | Compute isn't enabled yet. The next `compute` command enables it. |
| `Processing` | Datum is enabling Compute. This normally takes a few seconds. |
| `Active` | Compute is enabled, and every `compute` command runs normally. |
| `Unavailable` | Compute isn't available to your project. |

Add `-o json` or `-o yaml` to script against the state instead of parsing prose.

## Checking quota

Once active, `datumctl compute quota` shows how much of your project's compute allotment is used:

```bash
datumctl compute quota
```

```text
Quota for project acme-prod

RESOURCE    UNIT        LIMIT   USED   AVAILABLE   USAGE
Workloads   workloads   10      3      7           [######--------------]  30%
Instances   instances   50      12     38           [#####---------------]  24%
vCPUs       vCPUs       32      8      24           [#####---------------]  25%
Memory      MiB         65536   16384  49152        [#####---------------]  25%
```

Pass `--constrained` to show only the resource types that are currently at their limit — the fastest way to check whether a stalled rollout is a quota problem:

```bash
datumctl compute quota --constrained
```
